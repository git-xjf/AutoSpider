# AutoSpider 多智能体系统汇报提纲

核验日期：2026-10-27。配套详细说明：[AutoSpider 多智能体系统技术汇报](AutoSpider_多智能体系统技术汇报.md)。

## 1. 项目是什么

AutoSpider 是基于 DeerFlow 编排、MCP 工具接口和原生 HTTP/Playwright 执行器的数据采集系统。用户给出 URL 和字段、页数或条数，系统分析页面、形成计划、采样验证、执行全量并保存已验证工作流。

模型负责决策，程序负责可重复执行和规则验证。当前不需要 EasySpider 软件或上游执行程序。

## 2. 有哪三个智能体

- crawler-lead：总协调，理解需求、查询记忆、选择工具、启动执行、汇总交付。
- web-analyst：复杂页面的只读结构与传输分析，返回选择器、分页证据和不确定项。
- qa-repair：QA FAIL 后诊断质量问题，提出最小修复或重新分析建议，不自己启动全量任务。

它们按需工作，不是每次必须三个一起运行。

## 3. 提示词如何区分

Lead 有独立 SOUL.md；两个专家有各自 SYSTEM.md 模板，安装后写入 config.yaml。

最终 system 还包含框架安全规则、报告约定、技能和工具目录等；本次委派任务通过 HumanMessage 传入，而不是拼成高优先级系统指令。

## 4. 怎样协同、怎样通信

~~~text
用户 → Lead
Lead --task(prompt)--> Web Analyst / QA Repair
专家 --ToolMessage--> Lead
获准角色 --MCP--> 采集服务
~~~

后台 task_tool 把任务交给 SubagentExecutor。子角色新建自己的 messages，以系统提示词和任务 HumanMessage 为起点；完成后，结果用匹配 tool_call_id 的 ToolMessage 回到主图。

没有兄弟角色直接聊天；需要转交的证据由 Lead 放入下一次 task.prompt。具体代码见详细报告第 5 节。

## 5. 共享记忆吗

不共享完整聊天。要分清：

1. 当前对话历史：由主图 checkpoint 延续。
2. 子角色工作上下文：每次委派独立建立。
3. 站点记忆：SQLite 中的已验证规则与工作流，通过获准 MCP 工具访问。
4. 用户长期记忆：DeerMem 的用户摘要和 agent facts，主角色可按配置注入。
5. 临时浏览器 session：进程内状态，不保证跨角色仍有效。

跨角色应传有界证据和可重读句柄，不能假设只传一个 session_id 就等于共享浏览器。

## 6. Tools、MCP、Skills 有什么区别

Tool 是一次可调用能力；MCP 是工具服务接口；Skill 是场景工作方法和工具范围声明。

Lead 预绑定六个常用工具：记忆查询、工作流复用、HTTP 探针、HTTP 选择器验证、草稿创建、草稿执行。其他工具按需发现。

Web Analyst 只有九个只读业务工具；QA/Repair 只有六个验证、结果、日志与选择器工具。两个子角色不能再调用 task，也没有任务启动权限。

## 7. 爬取怎么真正执行

~~~text
自然语言 → 选择器/分页证据 → 类型化模型 → CrawlPlan
    → 固定执行器 → 样本 QA → 全量 QA → 结果与记忆
~~~

API 数据用 http_api；原始 HTML 数据用 http_html；必须渲染或交互时用 playwright。模型通常不临时生成一份新 Python 爬虫。

程序 QA 与 QA/Repair 智能体不同：前者执行规则，后者在失败后辅助诊断。字段非空和格式检查不等于证明全文语义正确。

## 8. 上下文与消耗如何控制

当前上下文摘要约在 32000 tokens 触发，按策略保留近期消息；摘要、委派记录和技能引用通过持久上下文重新投影。

Lead 配置累计 200000-token 防护，每次 run 最多两次普通 task 委派；两个专家分别有 12/10 回合和 300 秒限制。子角色还有独立 Token 防护，不能把它简单等同于 Lead 的预算。

紧凑探针、六工具预绑定、结果文件外置和已验证工作流复用，可减少重复输入；是否更快、更省仍需对照实验。

## 9. 本次必须如实说明的差异

- 运行中的 QA 角色磁盘提示词及已安装 crawl-validation 文本，比仓库模板旧。
- 父子技能白名单取交集：当前 Web Analyst 实际可见 transport-selection，QA/Repair 实际可见 crawl-validation。
- 当前三个角色可共用一个模型/API；GLM-5.3 实际是开启思考、low，不是彻底关闭。
- 原生子角色不自动继承父角色全部用户记忆。
- 站点库与运行目录是固定共享路径，不能声称已完成多租户隔离。
- 本次只写汇报文档，没有修复上述配置，也没有进行收费模型验收。

## 10. 结束语

这套系统采用中心协调式的按需多智能体，让不同角色在有界上下文和工具范围中完成分析、编排与修复，再由确定性执行服务和质量门控把计划转成可交付数据。

下一阶段重点是配置一致性、技能范围、资源预算、会话边界和多用户隔离，而不是单纯增加智能体数量。
