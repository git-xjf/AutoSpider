# v2 原型：现有技术与窄权项候选

核对日：2026-10-19。本文件只讨论专利候选；不认定可授权或不侵权。旧检索详见[10件专利对照](../memory-2026-10-19/PATENT_LANDSCAPE.md)。本轮增加动态依赖缓存与回归测试选择原始权项，防止把缓存、有限预算贪心测试换名后作为新颖点。以下“授权权项”指读过B/C文本，不是对现行法律状态的登记簿结论。

当前结论：v2 的完整合同输入投影、证书去重、局部失效、三态生命周期、冲突隔离、暂时不可访问分离和有限预算排序，能组成可检查的可靠工程方案；**目前没有足够依据将其认定为已找到可授权的技术核心。** 关键对照是具有相同完整投影的强缓存基线，不能只比较逐URL重复验证或缺失合同输入的弱基线。

## 1. 本次实际机制边界

已只读核对[原型core.py](../../../research/memory_v2/core.py)、[固定fixture生成器](../../../research/memory_v2/fixtures.py)及[独立测试](../../../tests/research/test_memory_applicability_v2.py)。实际范围为单一 `content` 字段的固定候选CSS选择器与确定性来源合同；没有自动生成合同、学习新选择器或自动修复规则的过程。`Rule.field_name`进入版本指纹，不等于已经实现多字段异构合同。

`observe_page`对全部已取得页面及候选计算selector匹配、非空性、Article/NewsArticle祖先、articleBody角色、列表标题与文章标题关系、页面URL与来源URL关系；`audit_evidence`读取这些已计算谓词进行状态分支。scope包括projector实现版本、origin、执行mode、规则指纹、合同指纹及全部facts；合同指纹又包含verifier实现版本。`MemoryStore`保存收据、隔离表及独立transport状态。

`VALID / INVALID / PENDING`是合同结果或最终决策状态；未审核的新scope可表现为没有数据库收据而输出PENDING，并非必然已有一条持久化PENDING记录。负例是当前精确scope的INVALID收据，不是自动学习出跨scope禁用条件。相同key的相反确定判定会quarantine；独立测试通过强制矛盾写入验证此防御，不应把这一注入案例计为确定性完整输入缓存自然产生的新识别能力。

`evaluate_policy`中的审核预算按“审核一个页面的全部候选”计数。即便预算为零，投影仍已完成所有页面和候选的核心关系计算。当前贪心目标为覆盖最多尚未缓存的scope实例，**未实现额外的差异严重度评分或竞争假设区分算法**。`counterexample_scoped`与`complete_projection_greedy`共用同一个调度分支及其后续存取、决策逻辑。

代码对应关系：

| 实现位置 | 能据此陈述的机制 | 不宜扩大为 |
|---|---|---|
| `observe_page`、`audit_evidence` | 显式公开microdata来源合同及其完整谓词投影 | 独立语义真值验证、任意网站合同发现 |
| `FieldEvidence`、`_scope_key`、`_validate_evidence` | 版本/规则/模式/来源域及facts内部一致性，检测事后修改 | 来自任意外部调用者的证据真实性证明 |
| `MemoryStore.lookup/record/quarantine` | 相同scope收据复用、相反收据隔离 | 自动故障根因学习、自动消解矛盾 |
| `evaluate_policy` | 有界页面审核及最大未覆盖scope覆盖排序 | 新的区分式主动探测或强基线以外的独立算法 |

边界必须保留：

- “完整”仅指包含所声明合同读取的全部输入，不表示证明文章事实或正文语义正确。合同本身若遗漏依赖，相同投影也可能对应不同真实正确性。
- 在已获取快照上少执行一次合同验证，不等于少一次HTTP请求、少一次模型调用或节省生产成本。只有实际测量相应操作才可提出该效果。
- 固定合同、固定选择器与离线快照验证，不等于在线自主生成新合同、自动发现任意语义漂移、通用LLM错误归因或真实网站自愈。
- 一个代表页的结果只可传播到具有相同合同版本、规则版本和完整投影的证据等价类，不能无依据传播到同路由所有页面。

## 2. 决定性常规部分

设合同版本为 `v`，确定性合同为 `C_v`，页面及任务公开证据的完整投影为 `P_v(x)`。若合同所有读取与控制流依赖均由投影决定，则：

`P_v(x) = P_v(y)  =>  C_v(x) = C_v(y)`。

这是固定函数对相同输入给出相同输出的性质。以 `(contract_version, rule_version, projection)` 为key复用结果，即函数缓存。使用哈希只是key编码方式；若只存哈希，应处理碰撞或核对规范化内容。证书命名、跨URL传播和字段粒度本身不改变这一逻辑。

同key出现相互矛盾的有效判定，说明至少存在遗漏依赖、合同非确定性、版本/证据关联错误或旧收据不一致。此时应停止该key的证书传播并隔离，不能以多数票恢复为有效。该防御有必要，但必要的防御规则不自动构成创造性。

另有必须测量的成本边界：投影若保留列表标题、文章标题等原值，不同实体页面往往无法合并；若改存“两个标题相等”等派生谓词，则生成投影已完成合同的一部分乃至核心判断。当前实现采取后一种方式：`headline_relation`、`source_relation`等在`observe_page`中得到，`audit_evidence`主要是少量条件分支。不能将这部分工作作为免费预处理，再仅以少调用一次verify声称节省。代码分别输出`projection_cost`、`audit_seconds`和`policy_seconds`，交底应保留这一成本分解；缓存实际收益还需比较总工作量、SQL/序列化和完整性检查开销。没有推迟的昂贵验证阶段时，证书缓存未必带来实际净收益。

内部binding检查可以发现构建后的facts或identity被改动，但不能证明调用者最初提供的HTML/facts真实。预计算observations是受信任研究接口，`MemoryStore.record`也信任审核器提交的Verdict；它可以接受人为构造的相反结果来测试隔离。本轮不把此受信任边界包装为外部证据认证机制。

## 4. 可以讨论的窄权项骨架

以下仅是让实现、证据和范围一致的交底候选，不是确认可授权的权利要求。不能删除限定后用“智能体记忆系统”概括替代。

一种网页字段抽取规则的适用性审核方法，包括：

1. 取得目标字段的可执行来源合同、合同版本及待复用规则版本；合同规定候选元素的来源角色、与任务实体的对应关系和判定所读取的输入。
2. 对当前已取得页面生成对应上述全部输入的规范化投影；将页面访问可用性与合同有效性分别记录，访问不可用时不产生规则无效反例。
3. 以合同版本、规则版本和完整投影确定证据等价范围；仅在该范围具有无冲突且有效的验证收据时复用合同判定。
4. 当投影或版本改变且无可复用收据时，把所涉范围置为待审核；保持不受该变化影响的范围状态。
5. 当新验证与同版本、同投影的旧收据矛盾时，把该证据范围隔离，停止其判定向其他页面传播，并保存冲突证据引用。
6. 在给定审核预算内，基于待审核范围影响的页面数量排序，验证代表页；仅将结果应用到同一完整证据等价范围，预算未覆盖范围保持待审核。当前实现是最大未缓存scope覆盖；若另主张差异信号或竞争假设区分，需新增实现和证据，不能写成已完成。
7. 对通过审核的范围记录与版本、投影及证据引用绑定的收据；任何后续规则/合同更新不得直接沿用原收据授权新版本。

该骨架的缺口是：第1–4、6–7步大部分可由D1–D6组合得到；第5步与访问状态分离是可靠性措施，尚未证明非显而易见。当前不宜把七步的并列写入视为创新已完成。

可能的从属限定只能取自实际实现并经检验的细节，例如：来源合同的具体公开元数据与实体对应断言、投影中缺省/空值的规范化规则、收据冲突撤销的精确范围、预算未覆盖状态的阻断条件。增加JSON字段名、哈希算法、固定阈值、角色名称等通常不能修补创造性缺口。

## 5. 强对照下必须允许的否定结论

至少比较“完整证据投影去重缓存”，并对齐合同输入、版本key、可用性处理和验证成本。另给该缓存同样的影响度/差异排序，才能区分缓存去重与调度贡献。

当前代码已经提供`complete_projection_greedy`强基线，并与candidate使用相同分支。相同初始存储、页面、规则、合同、预算下，两者审核顺序与决策等效是代码结构直接规定的事实；测试中存在对应等效断言。因此不能把若干测试集上的等效结果称为“新算法接近强基线”，也不能只展示优于FIFO/逐URL基线的结果而省略这条强对照。

| 观察结果 | 可以支持的结论 | 不能据此支持的结论 |
|---|---|---|
| v2优于每URL重复验证，但等同完整投影缓存 | 减少同输入的重复验证；工程上合理 | 已发明新的记忆适用性算法 |
| v2只因影响度排序在小预算下更好 | 指定负载下的审核顺序效果 | 通用最优probe、创造性已证明 |
| 增加相同排序后强缓存与v2等效 | 未显示超出缓存＋排序的额外效果；当前仍需新技术贡献 | 为了申请而把状态名/证书名当成区别 |
| v2只在强缓存遗漏冲突隔离/版本校验时更安全 | 发现基线实现完整性问题；相应防御措施应补齐再比较 | 基线缺陷必然构成新颖或非显而易见 |
| 两者都被同投影不同真值击穿 | 来源合同或投影不充分，需要缩小声称范围 | 已证明语义安全复用或不依赖oracle |

只有找到并实现现有方法无法等效处理的具体机制，且对齐强基线仍出现可重复的额外效果，才应更新为较积极的申请建议。若效果等同，应如实写入交底评估：**本轮原型验证了可靠性边界，未证明相对强现有技术的额外技术效果；该候选暂不建议仅凭现有结果提交发明申请。**
